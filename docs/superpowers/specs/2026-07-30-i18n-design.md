## 1. 目标与非目标

**目标**：界面与游戏数据名称同时支持 `zh-Hans`（简体中文）、`zh-Hant`（繁体中文）、`ja`（日文）、`en`（英文）四种语言，用户可在运行时切换并被记住。

**非目标（明确不做）**：

- 面向运维/开发者的数据校验诊断信息（如 `start2.json 数据校验失败（共 N 项）：`、`游戏基础数据版本错误，请先刷新游戏`）保持中文。这些出现在 `throw new Error()` 与 `console.error()` 里，读者是维护者不是玩家。
- `console.log` 的加载统计信息保持中文，理由同上。
- 不新增复数规则、日期/数字本地化——本项目界面上没有一处需要。

## 3. 地基约束：哪些字符串是身份键

本项目大量游戏数据字符串同时充当匹配键，**就地翻译会打断匹配链**。已逐一核对：

| 字符串 | 是否身份键 | 证据 |
|---|---|---|
| `equip.name` | **否**，纯展示 | 全仓库检索只命中模板渲染 |
| `ship.name` | **是** | `start2Store.ts:500` 的 `names.includes(ship.name)`；`:342` 的 `ship.name.includes('潜水')`；`sameShipList.ts:80`；`developmentPool.ts:54,57` |
| `开发池名称` | **是** | `existPool` 的元素、`selectablePools` 的去重键、`DevelopResult.池名`；`DevelopmentView.vue` 的 `onFlagshipSelect`/`selectResult` 用它做连接条件 |
| `ctypeMap` 的值 | **是**（今日数据下休眠） | `DevelopmentPoolClass.init()` 对非数字 `舰型` 做 `if (v === t)` 反查。实测当前 12 个 `舰型` 全是数字，该分支走不到——但仍按身份键对待，不依赖"今天恰好用不到" |

**结论**：所有译名一律是**旁挂查表层**，键为既有身份值（数值 ID 或中文池名），不修改任何身份值本身。

## 4. 架构：一套机制，两类内容

不引入 `vue-i18n`。理由：它只能覆盖 47 条静态文案，而装备名/舰名/舰级（ID 为键、按语言懒加载、原子发布、回退日文）与开发池名（键含中文与 `-`，会被其点号嵌套语法切开）都得另写一套——引入它的实际结果是项目里并存两套翻译机制。实测其体积为 19.0 KB gzip（全量）/ 14.0 KB gzip（runtime-only，且需额外引入 `@intlify/unplugin-vue-i18n` 构建插件）。本项目运行时依赖至今只有 `vue`/`pinia`/`vue-router`，且 `dataSchema.js` 是 328 行手写校验器而非引入 zod、测试用 `createApp().mount()` 而非 `@vue/test-utils`——既有品味一致地倾向"能写清楚就不引依赖"。

```
src/i18n/
  index.ts            # 门面：locale 状态、t()、名称查询函数、setLocale()
  types.ts            # Locale 联合类型、消息与名称表的类型
  detect.ts           # navigator.languages → Locale 的探测，纯函数
  messages/
    zh-Hans.ts        # 47 条 UI 文案（真值源，key 集合由它定义）
    zh-Hant.ts
    ja.ts
    en.ts
  names/
    poolNames.ts      # 46 个开发池名的四语言映射（人工翻译，编译进 bundle）
    stypeNames.ts     # 20 个舰种代码的四语言映射（人工翻译）
    load.ts           # 名称表的 fetch + 原子发布
src/components/
  LocaleSwitcher.vue  # 右上角语言下拉框
public/data/i18n/<locale>/{items,ships,ctype}.json   # 同步脚本产出
    # ja      : items/ships 为 {}（名称取自 start2），ctype 有内容
    # zh-Hans : 无 ctype.json（用既有的 ctypeMap），见 §4.2.1
```

### 4.1 A 层：UI 文案

扁平 key（不做嵌套），`zh-Hans.ts` 是 key 集合的真值源，其余三份用 `Record<MsgKey, string>` 约束——漏一条编译期就红：

```ts
// messages/zh-Hans.ts
export const zhHans = {
  'title.development': '装备开发',
  'label.fuel': '油',
  // ...
} as const

// types.ts
export type MsgKey = keyof typeof zhHans

// messages/en.ts
export const en: Record<MsgKey, string> = { /* ... */ }
```

`t()` 的签名是 `t(key: MsgKey): string`，拼错 key 编译期报错——这比 vue-i18n 的默认行为强。模板里的人体工学靠 `main.ts` 里一行 `app.config.globalProperties.$t = t` 提供（需在 `env.d.ts` 里补 `ComponentCustomProperties` 声明）。

### 4.2 B 层：游戏数据名称

文件形态 `public/data/i18n/<locale>/{items,ships,ctype}.json`，一律 `{ "<数值ID>": "译名" }`。用数值 ID 而非日文原名作键：`equipList`/`shipList` 本来就是 `id → info`，查表少一次转换，且避开同名歧义（日→译名的解析在同步脚本里一次做完）。

`ja` 的 `items.json`/`ships.json` 为空对象 `{}`，名称由 `start2.json` 直接提供。**不把日文名复制一份进去**——那会制造第二个真值源，`start2.json` 更新而同步脚本没重跑时会静默漂移。代价是同步脚本的覆盖率检查需要为 `ja` 的这两个文件写一处显式跳过（并打印跳过原因）；一处构建期特例，换掉一个永久的漂移隐患。

查询函数逐键回退到日文原名，**不回退到其他语言**：

```ts
export const equipName = (id: number) =>
  nameTables.value.items[id] ?? start2Store.equipList[id]?.name ?? ''
```

查询函数在渲染期读 `nameTables`（`shallowRef`）与 `locale`（`ref`），因此模板里直接调用即可获得响应性——语言切换后依赖它们的渲染会自动重跑，不需要额外的 `key` 强制重挂载。

#### 4.2.1 舰级名的特例：zh-Hans 不产文件

`public/data/ctype.json` 本身就是一份简体中文舰级名表，且已被 `developmentStore` 加载成 `ctypeMap`。若同步脚本再产出一份 `public/data/i18n/zh-Hans/ctype.json`，就是给同一份数据造了第二个真值源——而且复制的还是一份被哈希钉死、不可改动的文件。

因此舰级名的取数分两路：

- `zh-Hans`：读既有的 `ctypeMap`，不产文件、不发请求；
- `ja`/`zh-Hant`/`en`：读 `public/data/i18n/<locale>/ctype.json`，每份文件自身完整（派生失败的条目已填入日文原名），不需要跨语言回退。

这个分叉只存在于「舰级名从哪儿取」这一个查询函数里，对调用方不可见。作为交换，同步脚本必须做 §7 的自校验：派生出的 zh-Hans 舰级名与 `ctype.json` 在共有键上逐字相同——这既验证了派生算法，也证明两路取数在 zh-Hans 下是等价的。

查不到的 ctype ID 一律跳过不显示，与 `init()` 现有的 `if (ctypeMap[String(n)])` 行为一致。

### 4.3 A/B 之外：开发池名与舰种代码

- **开发池名 46 条**（`水雷系-32驱改二`、`空母系-五航改二(甲)` …）：wiki 无对应译名，由本次实施逐条人工翻译成 ja/en/zh-Hant，zh-Hans 即原名。键是中文原名，放独立的扁平映射 `names/poolNames.ts`，编译进 bundle（46×4 约 4 KB，不值得为它多一次网络往返）。
- **舰种代码 20 个**（`DD`/`CL`/`CVL` …）：出现在池描述里。放 `names/stypeNames.ts`，但**只手写三列**：
  - `ja` **从数据里取**，不手抄：池的 `舰种` 是代码字符串 → `ShipType[代码]` 得到 stype 序数（该枚举的序数就是游戏的 stype 值）→ `api_mst_stype.find(s => s.api_id === 序数).api_name` 得到日文名（`駆逐艦`/`軽巡洋艦`/`重雷装巡洋艦`…）。手抄这 20 个词只会引入错字风险，而数据里本来就有。
    **唯一的例外是 `FBB`**：`api_mst_stype` 里 `api_id` 8（FBB）与 9（BB）的 `api_name` 都是`戦艦`——游戏数据本身不区分这两个舰种，直接派生会让 `ja` 成为四语言里唯一分不清"战舰"和"高速战舰"的一个（`舰种` 含 `["BB","FBB",...]` 的池会渲染出`戦艦,戦艦`这种字面重复）。为此在 `names/stypeNames.ts` 加一条 `JA_STYPE_OVERRIDES = { FBB: '高速戦艦' }`，`stypeName` 的 `ja` 分支在查 `api_mst_stype` **之前**先查这条覆盖。这是有记录的单一例外，不是放弃"`ja` 全部数据派生"这条规则——其余 19 个代码仍然只从数据取。
  - `zh-Hans`/`zh-Hant`/`en` 手写：中文给全称（`驱逐舰`/`驅逐艦`），英文保留缩写本身（`DD`）——英文圈本来就用缩写。

  这也是 `start2Store` 保留 `api_mst_stype` 导出的**唯一理由**：与它同批的 `api_mst_equip_ship`/`api_mst_equip_exslot_ship` 因为没有任何消费者已被删除（见 §11），`api_mst_stype` 留下就必须有真实消费者，就是这里。

## 5. C 层：展示层改造清单

### 5.1 `FlagshipSearch.vue`

搜索谓词从「日文舰名 + 假名读音」扩展为「日文舰名 + 假名读音 + **当前语言译名**」。文件里那段注释明确写着当前前提是"项目里没有中文译名层 —— 简体输入「长门」搜不到「長門」"，本次改动使其失效，**注释必须同步改写**，否则会留下一段与代码相反的说明。

占位符文案 `输入日文舰名或假名读音` 相应改为四语言各自的表述（如 zh-Hans 改为 `输入舰名或假名读音`）。**这是唯一一处有意的 zh-Hans 措辞变更**，因为它描述的行为确实变了；已确认无测试断言该字符串。

建议列表里的 `{{ s.name }}（{{ s.yomi }}）` 改为展示译名，假名读音保留在括号里作为第二维度（对日文/英文用户，译名与原名相同或为罗马字，括号里的假名仍有意义）。

`归属开发池：{{ resolved.poolName }}` 里的池名同样是中文身份键，必须过译名层——与 §5.3 里结果表「秘书舰」列是同一个遗漏点，两处都要改。

### 5.2 `DevelopmentPoolClass` 的池描述

现状：`init()` 把舰种代码 + 中文舰级 + 日文舰名 + `['最低油','最低弹','最低钢','最低铝']` 拼成 `private text`，**在数据加载时就烤死成一种语言**；下拉框渲染的 `{{ String(pool) }}` 走的就是它。

改法：`init()` 产出结构化描述，拼句子搬到展示层的纯函数：

```ts
export interface PoolDescriptor {
  stypes: string[]              // 舰种代码，如 ['DD','CL']
  ctypes: (number | string)[]   // 数字 ctype ID，或非数字 舰型 的原始字符串
  shipNames: string[]           // 日文舰名（身份键原样保留）
  excludeShipIds: number[]
  shipIds: number[]
  minResources?: number[]       // 长度 4
}
```

约束：

- `init()` 里计算 `舰ID`/`舰ID集` 的四段逻辑**逐字不动**（对拍向量在校验它）；只替换 `text` 的构建。
- `init()` 签名不变（仍是 `(ctypeMap, getIDs, shipList)`），`tests/helpers/loadFixtures.ts` 因此无需改动。`ctypeMap` 仍然要传——非数字 `舰型` 的反查分支保留。
- 空描述的回退串 `过滤条件有点问题` 进 A 层，key 为 `desc.invalid`。
- 副作用：`private text` 正是 `DevelopmentView.vue:265` 与 `developmentStore.ts:setFlagship` 里两处 `as unknown as DevelopmentPoolClass` 的成因（Pinia 的 `UnwrapRef` 会丢掉 private 字段）。改成公开的 `descriptor` 后这两处 cast 可能不再必要——**跑 `pnpm type-check` 确认后再决定是否删除**，不预先假定。
- **`toString()` 的去向必须明确**：它现在是 `${开发池名称}(${this.text})`，`text` 一旦消失它就悬空。定为**只返回 `开发池名称`**，仅供日志与调试使用；模板不再渲染 `String(pool)`，改为调用格式化函数。不这么定死的话，`toString()` 极易变成第二个描述拼装器，与格式化函数各拼各的——正是这次重构要消除的东西。

### 5.4 样式：两处会静默错位的值

`assets/base.css` 里的注释明写这两个值是从中文推导的：

- `--form-label-width: 6.5em` 由「秘书舰类型：」6 个全角字符推出。英文 `Secretary Ship Type:` 会撑爆，导致下拉框与搜索框左边缘错开。
- `--app-font-sans` 是简中优先字体栈（`PingFang SC`/`Microsoft YaHei`/`Noto Sans CJK SC`），日文与繁中下会渲染出错误的地区字形变体。

改法：`setLocale()` 同步写 `document.documentElement.lang`，CSS 用 `:lang()` 分流，沿用既有的自定义属性机制不引入新概念。

`index.html` 里静态的 `<html lang>` 要一并设成 `zh-Hans`（与默认语言一致）——首帧在 `setLocale()` 跑之前就已经按它选字体栈了，留着默认值会造成一次可见的字体闪烁。

```css
/* 现有值 6.5em 留给 zh-Hans，取值依据见 base.css 既有注释 */
:root:lang(ja)      { --form-label-width: 7.5em; --app-font-sans: /* Hiragino Sans, Yu Gothic, Meiryo, Noto Sans CJK JP */ }
:root:lang(zh-Hant) { --form-label-width: 6.5em; --app-font-sans: /* PingFang TC, Microsoft JhengHei, Noto Sans CJK TC */ }
:root:lang(en)      { --form-label-width: 11em;  --app-font-sans: /* 拉丁优先 */ }
```

上表的宽度是按「最长标签的字符数 + 0.5em 右侧余量」估的初值（`ja` 的「秘書艦タイプ：」7 个全角字符、`zh-Hant` 的「秘書艦類型：」6 个、`en` 的 `Secretary Ship Type:` 按拉丁字符均宽约 0.5em 估），**实施时必须逐个用 `getBoundingClientRect` 实测校正**——现有注释里那句「实测 input.x - label.right === 0」说明这个项目对这类值是要量的，不是估的。校正后像现有注释那样写明每个值的取值依据。

## 6. 语言切换流程

沿用 `start2Store.readStart2()` 既有的「局部变量算完 → 最后原子发布」写法：

1. `setLocale(next)` 并发 fetch 该语言需要的名称文件——`items.json`、`ships.json`，以及 `ctype.json`（`zh-Hans` 不取，见 §4.2.1）；
2. **全部成功**才一起发布：写名称表 → 切 `locale` → 写 `document.documentElement.lang` → 写 `document.title` → **视情况**写 `localStorage`；
3. 任一失败：**停留在当前语言**并向用户提示，绝不出现「装备名换了、舰名还是旧的」的半成品状态；
4. 切换期间用 `pending` 标志禁用切换器，避免并发切换互相覆盖（后发起的请求先返回会写入旧语言的表）。

`localStorage` 只在**用户真正做出选择**时写：`setLocale` 带一个默认 `true` 的 `persist` 参数，`LocaleSwitcher` 触发的调用不传（走默认），`initLocale` 冷启动时显式传 `false`。理由是 §1 说的"用户可在运行时切换并被记住"——记的是"切换"这个动作，不是"这次探测/沿用到了什么"。若冷启动也无条件写入，一个从未手动选过语言、浏览器语言恰好是 `ja` 的首次访问用户会在什么都没点的情况下把 `ja` 写进 `localStorage`；此后 `initLocale` 读 `localStorage` 优先于探测，哪怕他把浏览器语言改回来，应用也不会再跟着变——这就是"记住选择"退化成了"缓存探测结果"，两者语义不同，退化后者是缺陷。

首次进入：`localStorage` 有值则用它（且校验值在 Locale 联合内，防止手改出非法值）；否则按 `navigator.languages` **逐个**探测，取第一个能识别的：

| 标签形态 | 判定 |
|---|---|
| `zh-CN` / `zh-SG` / `zh-Hans*` / 裸 `zh` | 简中 |
| `zh-TW` / `zh-HK` / `zh-MO` / `zh-Hant*` | 繁中 |
| `ja*` | 日文 |
| 其他任何标签 | 英文 |
| `navigator.languages` 为空或全不可识别 | 简中 |

裸 `zh` 归简中而非繁中，是因为不带地区的 `zh` 在现实中绝大多数来自简体环境；这是有意的默认，写进注释。探测逻辑放 `detect.ts` 的纯函数里（入参是 `readonly string[]`，不直接读 `navigator`），便于直接单测。

## 7. 同步脚本

新增 `pnpm sync-i18n --kc3 <path>`（沿用现有 `sync-data --from <dir>` 的形态，读本地 clone 而非联网）：

1. 读 KC3 的 `<locale>/{items,ships,ship_affix}.json` 与 `en/ctype.json`；
2. 装备：按 `start2.json` 的 `api_mst_slotitem` 建 `id → 日文名`，查 KC3 得 `id → 译名`；
3. 舰船：跑合成算法（`byId` → 精确 → 前后缀剥离后查基础名再拼回），得 `id → 译名`；
4. 舰级：`ja` 直接取 KC3 `en/ctype.json` 的值原样输出（该文件存的就是日文舰级名，不做派生）；`zh-Hant`/`en` 剥尾部 `型/級` → 查首舰译名 → 接回该语言的后缀（取自 `ship_affix.json` 的 `ctype` 映射），**派生不出的条目直接填入日文原名**，使每份 ctype 文件自身完整、运行时不需要跨语言回退机制。`zh-Hans` **不产出文件**，理由见 §4.2.1；
5. 写 `public/data/i18n/<locale>/*.json`，打印覆盖率、来源 commit 与文件哈希。

**硬性校验（不通过就非零退出，不静默回退）**：

- `DevelopmentPool.json` 引用的 102 件装备，在 `zh-Hans`/`zh-Hant`/`en` 三份 `items.json` 里必须全部有译名；
- start2 的 800 艘玩家舰在三份 `ships.json` 里必须全部有译名；
- `DevelopmentPool.json` 的 `舰型` 引用到的 ctype ID 必须全部可派生；
- **自校验**：派生出的 `zh-Hans` 舰级名，与现有 `public/data/ctype.json` 在共有键上必须逐字相同——已实测吻合（`Maestrale級`→`西北风级`、`Queen Elizabeth級`→`伊丽莎白女王级`），对不上即说明派生算法有问题；
- `ja` 的 `items`/`ships` 预期为空，跳过覆盖率检查并打印跳过原因。

不把 KC3 仓库作为子模块引入，只在 README 与脚本输出里记录来源 URL、commit 与 MIT 协议出处。

## 10. 已确认的数据版本偏移（既有问题，非本次引入）

`DevelopmentPool.json` 比 `start2.json` 新，两者不同期。

**证据**（全部来自数据本身）：

- `水雷系-32驱改二` 池引用舰ID `981, 982, 983, 1033`，后三个在 `start2.json` 里不存在。
- 第三十二驱逐队是玉波・涼波・藤波・早波。按 `api_aftershipid` 追改造链：

  | 舰 | 链 |

  | 藤波 | `485:藤波 → 373:藤波改 → 981:藤波改二` |
  | 玉波 | `674:玉波 → 718:玉波改`（到此为止） |
  | 涼波 | `675:涼波 → 710:涼波改`（到此为止） |

**已验证的上游数据源**：`Tibowl/api_start2`（`master`，2026-07-19 推送）确实有更新的数据，实测：

| 项 | 仓库内（2025-03） | Tibowl（2026-07） |

换上这份数据后，`DevelopmentPool.json` 引用的 102 件装备、全部直接引用的舰ID、全部 `舰名` 都能查到——**池数据与舰船数据完全自洽**，`水雷系-32驱改二` 池也能匹配到全部四舰。舰船与装备的**记录字段结构没有变化**（`api_aftershipid` 仍是字符串）。

**但实测换入后 1203 项测试有 213 项变红**，分两类原因：

1. **上游改了 `api_mst_equip_ship` 的形状**（这是事先没人能预料到的一条）：

   | | 形状 |
   |---|---|
   | 旧 | 数组 `[{api_ship_id: 100, api_equip_type: [1,2,4,...]}]` |
   | 新 | 对象 `{"100": {api_equip_type: {"1": null, "27": [268], ...}}}` |

   `validateStart2Payload` 因此报 `api_mst_equip_ship 缺失或不是数组` 并拒绝整份 payload——**应用会直接判定数据加载失败、什么都不渲染**，不是局部降级。

   好消息是这条的修复成本很低：该表在本项目里只喂给 `打孔装备` / `打孔装备图标` 两个字段，而这两个字段**只写不读**——全项目没有任何组件或 core 模块消费它们。可以照 `App.vue` 里删除「只写不读」状态的先例整段删掉，或写一个形状适配器。

2. **对拍基准过期**（207 项在 `tests/oracle.spec.ts`，另有 4 项在 `sameShipList.spec.ts`）：多了 62 艘舰，开发池的 `舰ID` 展开结果随之改变，`vectors.json` 记录的基准不再适用。`sameShipList.spec.ts` 里「链数与覆盖舰数与参考实现一致」那几条同理。

**为什么本次不修**：

第 2 类是硬阻碍。`vectors.json` 与 `sameShipList` 的期望值都源自参考实现（C# 版），而**生成它们的工具不在本仓库内**——这不是能靠改代码绕过去的，`pnpm test` 在本仓库内无法恢复全绿。第 1 类反而是小事。

同时，这件事**与多语言完全正交**：舰名译名表由同步脚本按当前这份 start2 生成，start2 里有多少舰就译多少舰，永远自洽；将来换了新数据只需重跑一次 `pnpm sync-i18n`，不改任何代码。

**当前的实际影响**（本次改动前后一样）：`水雷系-32驱改二` 池只能匹配到藤波改二一舰，另外三舰因数据里不存在而无法被秘书舰搜索命中。这是数据新鲜度问题，翻不翻译都存在。

**要升级 start2 该怎么做（独立工作项，不在本次范围）**：

1. 取 `Tibowl/api_start2` 的 `start2.json`（注意该仓库未声明协议）；
2. ~~适配或删除 `api_mst_equip_ship` 相关处理~~ —— **已完成**，见 §11；
3. 在能访问参考实现的环境里重新生成 `tests/fixtures/vectors.json`，并核对 `sameShipList.spec.ts` 的期望值；
4. 两者一起提交，然后重跑 `pnpm sync-i18n` 刷新译名表。

第 3 步是唯一无法在本仓库内完成的。

## 11. 已完成：删除只写不读的打孔装备计算

在多语言实施之前先做掉的一步（§10 升级路径的第 2 步）。

**改动**：删除 `readStart2()` 里计算 `ship.打孔装备` / `ship.打孔装备图标` 的整段逻辑，连同 `api_mst_equip_ship` / `api_mst_equip_exslot_ship` 两个 store ref 与导出、`Api_Mst_Equip_Ship` 等四个类型声明、`dataSchema.js` 里对这两张表的校验，以及随之失去测试对象的 2 条断言。

**理由不是"这是死代码"，而是"我们在校验一个自己不读的字段"**。上游把 `api_mst_equip_ship` 从数组改成对象后，继续校验它意味着：为了满足一个自己写的校验器，去适配一份自己根本不消费的数据——代价是整份 payload 被拒、应用白屏。不读就不校验。

**验收不是"1203 项仍全绿"**——那删掉任何代码都能满足，只证明没弄坏别的。真正的验收是把新 start2 换入后跑一遍：

| | 改动前 | 改动后 |
|---|---|---|
| 失败断言 | 213 | **211** |
| 失败文件 | 4 | **2** |

清掉的两条正是 `dataSchema.spec.ts` 与 `syncDataValidate.spec.ts` 的正式数据校验——`validateStart2Payload` 现在接受新 payload。剩余 211 项（`oracle` 207 + `sameShipList` 4）全部是对拍基准过期，属第 3 步。

`api_mst_stype` 保留（形状未变），它的消费者见 §4.3。
